1. System Overview

Gator Enterprise is the organizational control plane for AI-assisted engineering governance. It answers: "Can you prove the AI understood the module, and did a human verify that understanding before the change?"

It does this by:

  • Ingesting Git commits from connected repositories via GitHub webhooks
  • Extracting governance evidence from each commit (trailers, charters, status.json)
  • Comparing evidence against organizational policies (drift detection)
  • Projecting fleet-wide compliance status through read-model views
  • Providing operator access via REST API and CLI
Key principle: Enterprise is deterministic — no AI in the control plane. Evidence comes from Git, reports come through the API. All analysis is rule-based comparison, not inference.

3. Data Flow

The core pipeline is a chain of automated steps triggered by Git activity:

GitHub Push Event │ ▼ ┌─────────────────┐ Webhook signature verification (HMAC-SHA256) │ POST /webhooks │────▶ Resolve provider from installation_id │ /github │ Create ingest job: register_commit_metadata └─────────────────┘ │ ▼ (Worker picks up job) ┌─────────────────┐ │ register_ │────▶ Create Commit record (idempotent — dedup by SHA) │ commit_ │ Auto-enqueue: extract_commit_observation │ metadata │ └─────────────────┘ │ ▼ ┌─────────────────┐ │ extract_ │────▶ Fetch governance artifacts from repo via provider API: │ commit_ │ • .gator/status.json (presence + hash) │ observation │ • .gator/constitution.md (presence) │ │ • .gator/charters/*.md (count + names) │ │ • Commit message trailers (Gator-*) │ │ Store as CommitObservation │ │ Auto-enqueue: evaluate_drift └─────────────────┘ │ ▼ ┌─────────────────┐ │ evaluate_ │────▶ For each active policy targeting this repo: │ drift │ Compare observation against policy requirements │ │ Upsert PolicyDriftFinding per check │ │ Severity: aligned | drift └─────────────────┘ │ ▼ ┌─────────────────┐ │ E5 Views │────▶ Fleet summary, repo detail, policy compliance, │ (on-demand │ timeline — all read live from the tables above. │ reads) │ No lag, no materialization delay. └─────────────────┘
Auto-chaining: Each job automatically enqueues the next step. A single GitHub push event triggers the entire pipeline without manual intervention: commit → observation → drift → live in views.

Reconciliation

In addition to webhook-driven ingest, the worker runs periodic reconciliation on a configurable interval. This catches commits that arrive while webhooks are down, and syncs the full repository inventory from the provider API.

4. Policy Engine

Policies define what governance requirements a repository must meet. They are versioned, targeted, and rolled out deterministically.

Create Policy (draft) │ ▼ Create Version(s) — immutable after creation │ content: JSON governance rules │ content_hash: SHA-256 fingerprint ▼ Activate Version ─────▶ Deactivates previous active version │ Creates PolicyRollout (pending) for each target repo │ Enqueues drift re-evaluation ▼ Add Targets ──────────▶ Associates repos with policy │ Creates rollouts if active version exists ▼ Rollout State Machine: ┌───────────────────────────────────────┐ │ pending ──▶ applied │ │ ──▶ failed │ │ ──▶ superseded (newer version)│ │ │ │ applied ──▶ outdated (newer activated)│ └───────────────────────────────────────┘

Policy Content

A policy version's content is a JSON object defining governance checks. Current supported checks:

Check NameWhat It Verifies
charter_requiredAt least one charter file exists in .gator/charters/
status_json_required.gator/status.json is present and valid
trailers_requiredCommit message contains Gator-* governance trailers

Invariants

  • Versions are immutable — content and content_hash never change after creation
  • At most one active version per policy (enforced by partial unique index)
  • Activation is idempotent
  • Non-terminal rollouts (pending, applied): at most one per (policy, repo) pair
  • Supersession is explicit — new activation supersedes existing pending rollouts

5. Compliance State Machine

Every repository is classified into one of six compliance states. This is the core abstraction for fleet visibility.

Evaluation Precedence (first match wins): 1. Any rollout in FAILED state? ──▶ FAILED 2. Any rollout in PENDING state? ──▶ PENDING 3. Observation after max(applied_at)? ├── No observation after rollout ──▶ UNKNOWN ├── Has drift findings (severity=drift) ──▶ DRIFTING └── No drift findings ──▶ ALIGNED 4. No active policy targets? ──▶ UNGOVERNED

ALIGNED

Policy applied, observation exists from a commit after rollout, zero drift findings. The intended state.

DRIFTING

Policy applied, observation exists, but one or more governance checks failed. Needs attention.

PENDING

Policy targeted but rollout not yet applied. Compliance cannot be assessed. Expected to resolve.

FAILED

Rollout application failed. Operational issue — requires operator intervention.

UNKNOWN

Policy applied but no commits observed since. Waiting for new activity.

UNGOVERNED

No active policy targets. The repo is tracked but not subject to any policy.

Critical invariant: Observations are only considered if the commit happened AFTER the latest rollout's applied_at timestamp. Pre-rollout evidence does not count. This prevents a repo from appearing "aligned" when the policy hasn't actually been tested against new activity.

Bearer token in Authorization header. Tokens are SHA-256 hashed and stored. Every request includes X-Request-ID in the response.

7. Operator CLI

The gator-enterprise CLI is a pure HTTP client — no shared runtime with the service.

pip install -e enterprise/enterprise-cli/

export GATOR_ENTERPRISE_URL=https://gator-enterprise-dev.fly.dev
export GATOR_ENTERPRISE_TOKEN=your-token-here

Commands

# Identity
gator-enterprise auth whoami

# Repositories
gator-enterprise repos list
gator-enterprise repos refresh <repo-id>
gator-enterprise repos policies <repo-id>

# Providers
gator-enterprise providers list
gator-enterprise providers reconcile <provider-id>

# Policies
gator-enterprise policies list
gator-enterprise policies get <policy-id>

# Reports
gator-enterprise reports runs

# All commands support --json for machine-readable output
gator-enterprise repos list --json

10. Getting Started

Prerequisites

  • Python 3.11+
  • PostgreSQL instance (Fly.io Postgres, or local)
  • GitHub App with webhook configured (for commit ingest)

First-Time Setup

# 1. Clone and install
cd enterprise
pip install -r requirements.txt

# 2. Set environment
export DATABASE_URL=postgresql://user:pass@host/dbname
export APP_ENV=dev
export GITHUB_WEBHOOK_SECRET=your-secret

# 3. Run migrations
alembic upgrade head

# 4. Bootstrap org + admin token
python -m app.admin bootstrap
# → Prints raw admin token (save it!)

# 5. Start API
uvicorn app.main:app --reload

# 6. Start worker (separate terminal)
python -m app.worker

# 7. Register GitHub provider
python -m app.admin register-provider \
  --type github \
  --config '{"app_id": "123", "installation_id": "456"}'

First Policy

# Create a policy
curl -X POST $URL/api/v1/policies \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name": "Charter Required", "slug": "charter-required"}'

# Create a version with governance rules
curl -X POST $URL/api/v1/policies/$POLICY_ID/versions \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"content": {"checks": ["charter_required", "trailers_required"]}, "notes": "Initial policy"}'

# Activate the version
curl -X POST $URL/api/v1/policies/$POLICY_ID/activate/$VERSION_ID \
  -H "Authorization: Bearer $TOKEN"

# Target repos
curl -X POST $URL/api/v1/policies/$POLICY_ID/targets \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"repository_ids": ["repo-uuid-1", "repo-uuid-2"]}'

# Check fleet status
gator-enterprise auth whoami
gator-enterprise repos list
gator-enterprise policies list

Verify the Pipeline

# Push a commit to a targeted repo, then:
curl -H "Authorization: Bearer $TOKEN" $URL/api/v1/views/fleet | python -m json.tool

# You should see the repo transition from "pending" or "unknown"
# to "aligned" or "drifting" depending on governance state.
