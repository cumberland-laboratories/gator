A migration has three truths: what the old system does, what the new system promises to preserve, and how the new system works. Gator keeps each in its own charter, so an agent loads only the one the change needs.

Why migrations need their own charter structure

Without structure, migration knowledge accumulates in one chronological charter. Legacy behaviour, porting decisions, review findings, retired designs and target implementation details pile up together, and a single charter can grow to thousands of lines. Every change then loads all of it.

Reviewers must recover a small number of active invariants from that history. Relevant constraints become hard to locate, contradictions are easy to import from superseded milestones, and new findings are appended as more prose instead of sharpening a small current contract. Review rounds repeat because the governing context is too large and too historical. Some findings will always be ordinary implementation mistakes; the structural problem is that the map stopped being a map.

The goal is a sharper active map, not a loss of institutional memory. History stays in Git and artifacts; charters hold what is true and binding now.

Three layers of charters

Figure 1 — three families of charters, each answering one question, with a small shared hub. Arrows show the direction of authority: observed behaviour informs the contract, and the contract governs the implementation.

Legacy source

What does the original system actually do?

Owns

  • canonical entry points and call paths
  • source data reads and writes
  • ordering, deduplication, missing-value and stateful-processing semantics
  • hard-coded parameters and lookup behaviour
  • ambiguous variants and unresolved questions about the production source
  • source-specific tripwires that a port must understand

Does not own

  • target implementation details
  • “ported at milestone X” chronology or deployment history
  • accepted divergences (it links to the contract)

Lifecycle: relatively frozen after the source baseline is established. It changes only when evidence corrects our understanding of the old system.

Migration contract

What equivalence or intentional difference are we committing to, and how will we prove it?

Owns

  • the source-to-target semantic mapping
  • invariants that must survive the migration
  • explicitly accepted divergences and their rationale
  • source precedence when references disagree
  • parity fixtures, acceptance gates and cutover evidence
  • temporary safeguards and their removal conditions
  • open decisions that materially affect equivalence

Does not own

  • complete descriptions of either codebase
  • a log of every review finding and fix
  • retired design alternatives once a decision is final

Lifecycle: active during the migration. At cutover it shrinks to the few permanent compatibility constraints, or moves out of active routing into an archival artifact.

Target implementation

How does the replacement work now?

Owns

  • current public surfaces and module ownership
  • function names and dependency direction
  • tables, files, procedures, privileges and other external state read or written
  • active operational and security tripwires
  • negative space: what the module deliberately does not do
  • links to the contract where behaviour is parity-sensitive

Does not own

  • milestone-by-milestone landing history or superseded designs
  • detailed test transcripts or review IDs
  • repeated explanations of the old system’s behaviour

Lifecycle: survives the migration as an ordinary code charter, edited in place as behaviour changes, never with a new “landed in milestone N” section per increment.

A small migration-cross-cutting.md holds the rules that span all three layers: authority, source precedence, change routing, shared invariants and evidence tiers. It is a hub, not a fourth lifecycle layer, and it must not become another milestone history.

One fact, one owner

Every material fact has exactly one authoritative charter. Other layers link to it instead of restating it.

Take a deduplication rule: when two records match, which one wins?

FactOwner
The old system keeps the first matching record in file orderLegacy source charter
Whether the new system must match that, and any accepted divergenceMigration contract
How the new code’s ordering and tie-breaker implement the current behaviourTarget implementation charter

This prevents three similar paragraphs from drifting apart, and it forces reviewers to keep three things distinct: observed source truth, migration policy, and implementation mechanism.

Source precedence

Observed executable behaviour of the old system outranks its comments and plans. The active migration contract decides whether the target must match or intentionally diverge. The target charter describes how the approved contract is implemented; it cannot silently redefine the contract.

Route each change to the smallest charter

The value of the split comes from selective routing. Three sections in one large file would keep the same context problem. INDEX.md maps precise code paths to the smallest target charter, and names the legacy and contract charters as conditional context.

ChangeCharters to read and update
Internal refactor, behaviour unchangedThe target charter only
Change to output ordering or matching semanticsTarget charter + the migration contract
Newly discovered behaviour of the old systemLegacy charter; the contract too only if the promise changes
More parity fixtures, no contract changeTarget test entry or a test artifact; do not rewrite the legacy charter
Deployment-driver changeTarget deployment charter; the contract only if cutover evidence changes
Rule

Never touch all three layers merely to satisfy a hook. A charter changes only when a fact it owns changes. Code changes normally touch one target charter.

Shared migration invariants

These belong in the cross-cutting charter, because they apply to every step of the migration:

  • Parity claims require executable evidence, not code-shape similarity.
  • Ordering, missing values, field widths, duplicate selection and stateful processing are business behaviour whenever the old system makes outcomes depend on them.
  • Intentional divergences are named in the contract, with a bounded scope and a fixture or operational gate.
  • Dynamic identifiers are validated before they are interpolated, and destructive targets fail closed.
  • Production source data stays read-only during the migration unless an Architect-approved cutover contract says otherwise.
  • Full-scale runs stay guarded until retained evidence establishes a safe operating envelope.

Evidence tiers

  1. Local unit and structural tests prove helper and construction contracts.
  2. Test-environment parity fixtures prove deployed behaviour on controlled data.
  3. Probes against real data prove shape, cost, scale and operational safety.
  4. Trusted outputs from the old system prove business parity, when they are available.
Rule

Passing a lower tier never implies that a higher tier passed.

Keep every charter small

The structure only helps if each charter stays sharp. The layers must enforce the charter guide, not reproduce the old content under more file names.

  • Aim for 30–80 lines per charter; split at around 100.
  • Keep function entries to roughly 3–5 lines plus true tripwires.
  • Describe the current state, not the sequence by which it arrived.
  • Put SQL fragments, test matrices, review dispositions and performance evidence in artifacts or test files.
  • Link to an artifact for deep rationale; do not paste the artifact into a charter.
  • Replace obsolete statements instead of keeping them “for history”. Git has the history.
  • A tripwire must change an implementer’s behaviour. A note that does not constrain work is not a tripwire.

File layout and templates

Keep all migration charters directly in .gator/charters/, with a family prefix. Do not nest them in subfolders: the pre-commit hook matches staged charters by file name, so nested paths cause false charter-index-gap failures. Split target charters by code domain, not by milestone.

.gator/charters/
  migration-cross-cutting.md

  legacy-<system>-<area>.md
  migration-<step>-contract.md
  target-<platform>-<domain>.md

Start each family from a template:

Adopting the structure: start with a pilot

Restructure one step first, the one with the most review pressure and the clearest overlap between source semantics, migration decisions and target implementation.

  1. Finish any in-flight product change first. Do not mix a governance rewrite into a product-code diff.
  2. In a separate, governance-only commit, extract that step’s material from the oversized charters.
  3. Build the first three-file chain: legacy charter → migration contract → target charter.
  4. Add a narrower target charter if the remaining material would push a target charter past the size limit.
  5. Rewrite INDEX.md so work on that step loads only the cross-cutting charter, its target charter, and the contract when semantics or parity change.
  6. Run the next change under the new routing. Watch whether review findings become fewer, more local and less repetitive.
  7. If the pilot works, apply the structure to the other steps, each in its own governance-only commit.

Do not delete information during the pilot. Material that is valuable but not charter-shaped moves to an artifact or stays recoverable in Git.

How you know it worked

  • A change in one area can be reviewed without loading the history of unrelated areas.
  • Each important invariant has a single obvious authority.
  • Target code changes normally touch one target charter, not three layers.
  • Retired milestone wording no longer competes with current contracts.
  • Pre-commit charter findings become specific rather than bulk noise.
  • Review rounds converge on implementation defects instead of rediscovering scope and source-precedence questions.
  • A new reviewer can explain the source behaviour, the migration promise and the target mechanism without confusing them.
