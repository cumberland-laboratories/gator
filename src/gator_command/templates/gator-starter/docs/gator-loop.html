A Loop gives you a structured way to move from an idea to an approved plan, and then to reviewed code, with the whole decision trail kept in the repository.

When to use a Loop

  • Use a Loop for work that deserves a second opinion. A change that crosses several modules, touches something risky, or needs a real design benefits from one agent writing and another agent checking. Two different models catch different mistakes.
  • Use an ordinary session for everything else. A small fix, a clear refactor, or a documentation update does not need a Loop. Ask your agent directly.

Three roles

Two agents do the work. You make the decisions.

Figure 1 — the agents never talk to each other directly. Every step goes through Gator, which checks whose turn it is and keeps the record.
  • Architect. You start the Loop, watch it, and make every decision that matters. Only you can pause it, redirect it, or end it.
  • Draftor. An AI agent that writes: first a plan, then the code that carries it out.
  • Reviewer. A second AI agent, ideally a different model, that checks the Draftor's work and approves it or asks for changes.

From an idea to an approved plan

Figure 2 — the plan goes back and forth until the Reviewer approves it, or until you step in.
  1. Write a sketch. Describe what you want, what is out of scope, and any decision you have already made. A few paragraphs are enough.
  2. The Draftor drafts a plan. It reads the repository's charters, then turns your sketch into a concrete plan.
  3. The Reviewer reviews it. It approves the plan, or it lists what must change.
  4. The Draftor revises. The plan goes back to review. This repeats until the plan is approved.
  5. The plan is approved. It is now a fixed, reviewed record of what will be built.

From an approved plan to reviewed code

Figure 3 — the code is built and reviewed in steps. Nothing is committed until you commit it.
  1. Start a coding Loop from the approved plan. The plan can divide the work into checkpoints.
  2. The Draftor builds one checkpoint. It makes the changes and stages them for review.
  3. The Reviewer reviews the exact code. The approval covers the code that was submitted, not a description of it. Each checkpoint is approved before the next one starts.
  4. You commit. After the last approval, you make one normal commit. The Loop then confirms that the committed code is the code that was approved.

You stay in charge

The agents propose and check. You decide.

  • Pause. Stop the Loop at any point and pick it up later where it left off.
  • Clarify. Send guidance to the agent that is working, or answer a question an agent has escalated to you.
  • Redirect. Give more rounds to a plan that is close, or send approved code back for another review.
  • Approve the result. An approved plan or approved code is a recommendation. It becomes part of the codebase only when you commit it.
  • End. Stop the Loop for good when the idea has changed. The record stays, so you can see what was tried.
