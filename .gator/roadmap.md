## Product

One product: **Gator** — Git-native governance for AI-assisted engineering. Ships as `pipx install gator-command`. Open source under **Apache License 2.0** (see [`LICENSE`](../LICENSE) and [`NOTICE`](../NOTICE); the MIT → Apache 2.0 flip landed in Phase 3c, 2026-08-01). ## Current Priority

**Architect-set 2026-08-17** (supersedes the same-day post-tranche reset): the post-v2.8.0 reality is that per-branch shipped runtime has become a product-growth constraint, not just an agent-education problem. The near-term window therefore shifts from “teach the agent to survive cross-branch drift” to “remove the runtime duplication that causes the drift,” while preserving the repo-side governance record. Blueprints 2.0 remains important, but it moves behind this architecture change.

1. **Machine-scoped Gator runtime + policy channel (`~/.gator/`) — remove per-branch shipped-runtime friction at the root.** *(Architect-ratified 2026-08-17.)* The user-facing pain is now judged too large to leave as merge procedure overhead: shipped `.gator/.includes/` runtime duplicated into every branch creates update churn on every repo, every branch, and every merge, and that friction is severe enough to limit user growth. The right move is the **runtime/policy split** sketched in `vault/artifacts/2026-08-17-gator-all-branches-update-and-machine-scoped-runtime-design-note.md`: repo-scoped governance record stays in Git; machine-scoped runtime moves to `~/.gator/runtime/<version>/`; Enterprise policy distribution uses the same machine channel rather than being stomped on by `gator update`. This is **not** a small cleanup — expect roughly a sprint of design + implementation. First-pass phase shape:
   - **Phase 1 — design + trust boundary.** Ratify exactly what stays repo-side vs moves machine-side; choose the repo-side runtime pin/manifest surface; define the old-commit and no-install fallback behavior; answer the “proof lives in Git” objection explicitly.
   - **Phase 2 — runtime resolver + materialization.** `gator init` / session-open path materializes and refreshes `~/.gator/runtime/<version>/` from the installed wheel, with explicit behavior when the installed CLI is older/newer than the repo pin.
   - **Phase 3 — hook/script cutover.** Repo hooks and shipped script callers resolve through the machine runtime instead of `.gator/.includes/scripts/`; keep pre-split compatibility for older commits and repos during the migration window.
   - **Phase 4 — repo-side shrink + migration.** Reduce repo-shipped machinery to policy + record + pin/manifest; collapse cross-branch runtime drift from “many file conflicts” to a small mergeable version surface; document migration and rollback.
   - **Phase 5 — Enterprise policy channel.** Make org/repo policy distribution through `~/.gator/` first-class on top of the same machine runtime seam, with repo-side evidence of what policy/version governed a commit.
   This is now the most important structural product fix on the board because it directly serves both adoption and future fleet policy control.

2. **Gator + Enterprise: polished and ready for lots of users.** Two halves of one readiness goal. **(a) Gator general polish** — ridiculously easy to install and use: Dashboard-first UX, one-command install, zero-config governance; every rough edge in install/onboard/update is a priority bug. Backlog: "Building — Priority 1: Post-Install Onboarding & UX" table below, the vaulted-docs rewrite (`installation.md` / `upgrade.md` / `getting-started.md` / `index.md` for the pipx-first world — open inbox item since 2026-08-02), and open issues #1 (dashboard swallows update errors) and #4 (actions Node.js bump, deadline-driven). **(b) Enterprise at "polished demo" level** — the audit surface is evaluator-ready; getting it to polished-demo means the packaging + operability arc in Post-2.6 candidate work: **item 5 single-pipx install (the announcement blocker)**, item 6 cross-OS blob-store defaults, item 3 bundled pre-commit sync, item 4 session-block retirement, item 7 fresh-machine bootstrap, plus the quality tail (items 16/17/12).

3. **Blueprints 2.0 — HTML inspection surfaces for the human Architect.** *(New 2026-08-17.)* Interactive HTML blueprints that let the Architect navigate the codebase the way an effective AI model does — charter-first, progressive-disclosure — restoring the Architect to actual code review instead of "babysitting LLMs": dissecting how a feature works, or what a function does and does not do. Starter experiment exists (`.gator/vault/blueprints/charter-flowchart-high-level.html` — interactive charter-module map with click-through to covered files/functions). The design basis is the four-level progressive-disclosure model from the supporting artifacts: **Level 1** charter map (intentional architecture) → **Level 2** charter → covered files/surfaces → **Level 3** architecturally-significant functions (callers/callees/state/tripwires, aggressively curated) → **Level 4** drift map (charter-declared vs code-observed structure — inspection prompts, not verdicts). Core insight: *the charter graph is the intentional model, the code graph is the observed model, and inspection happens at the boundary between them.* Potentially a very big deal — an architecture-truth surface, not a visualization novelty. See "Building — Priority 2: Blueprints 2.0" below for the concrete backlog and supporting-artifact references.

4. **Gator Loop: smooth the rough edges.** The loop works end-to-end — all 12 subcommands shipped. What remains is Dashboard integration (events timeline, session card) and protocol refinements from real usage. Tracked as GitHub umbrella [#5](https://github.com/cumberland-laboratories/gator/issues/5) with children #6/#7/#8 and the "Building — Priority 3: Gator Loop Polish" table below. Explicitly below Blueprints 2.0 per Architect direction 2026-08-17.

5. **Normalized transcript index (exploratory, below Loop).** Optional, rebuildable message/tool-call index layer over Enterprise transcript custody — raw blob stays the source of truth. Post-2.6 candidate item 18; design note: `vault/artifacts/2026-08-17-gator-normalized-transcript-index-design-note.md`.

## Strategic Direction

- **Open source distribution** (Apache 2.0) for both the core CLI and Enterprise capabilities
- **Maximum developer adoption** through frictionless installation
- **Dashboard-first product surface** — CLI commands become internal implementation details
- **Multi-agent governance** — gator loop as the foundation for governed AI collaboration

### Building — Priority 1: Post-Install Onboarding & UX

The `.exe` installer is deferred — the target audience (developers using AI tools) has Python and CLI fluency. The real gap is what happens after `pipx install gator-command`.

**v2.4.x baseline shift (2026-07-30)**: the retire-gator-install release train (v2.4.0-v2.4.2) collapsed the whole install/update surface into a much simpler shape:

- **`gator gatorize`** — installs on the current branch, in place. Prints a scenario-aware pre-action summary, asks a single Y/n gate, refuses on a dirty tree under `--yes`. No branch-dance, no merge-back-to-dev ritual, no `gator-install` branch to explain in every install doc.
- **Dashboard Update** — invokes `gator-update` on the current branch. Result is exactly what the button label says. No silent branch switches, no cross-branch contamination. Non-interactive fragility is gone (`--yes` propagates cleanly, self-heal recovers from stale `product-source.json`).
- **Dashboard Gatorize** (Fleet-row button, ungoverned repos) — its own dedicated `/api/repo/<name>/gatorize` endpoint. No more self-referential 400s.
- **Fleet Version column** — stamps on every update, so drift is visible and Update-button enable/disable is trustworthy.
- **Recovery messaging** — the safety-branch pattern (`git checkout -b my-gator-experiment` BEFORE running gatorize) is the documented supported clean-undo path. Scoped git-native recipes for uncommitted / committed / untracked-file cases. No overclaiming.
- **Codebase** — ~2400 lines of retired bash / template gatorize.py deleted. Fewer surfaces to audit, fewer scenarios to explain, fewer failure modes to document.

### What Enterprise adds

Enterprise capabilities build on top of the core Gator install — they don't replace anything. The activation surface is `gator enterprise` as a CLI subcommand group:

```
gator enterprise activate     — one-time machine setup (creates ~/.gator/enterprise/, installs global git hooks, registers machine)
gator enterprise sync         — pull hook-policy and org policies from Enterprise
gator enterprise repo init    — provision a repo for Enterprise governance
gator enterprise transcripts  — pull/list/show/get/link session transcripts (--vendor claude|codex|gemini)
gator enterprise commits transcripts <sha>   — Q1: which transcripts touched this commit
gator enterprise commits list --repo <id>    — Q2: which recent commits have transcript coverage
gator enterprise transcripts list --unlinked — Q3: which recent transcripts are still unlinked
gator enterprise commits provenance <sha>    — Q4: which machine produced this commit
gator enterprise repos transcripts <id>      — Q5: which vendor sessions touched this repo over time
```

This keeps Enterprise as a feature of Gator, not a separate product. Same install, same CLI, same repo. Enterprise adds:

- Session evidence capture and storage
- Fleet-scale audit and reporting
- Centralized policy management
- Git provider integrations (GitHub App, webhooks)
- API-first fleet visibility
