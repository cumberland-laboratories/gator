What this shows

Every entity that participates in the loop, and every arrow the loop can travel. Four role nodes across the top (Draftor, Reviewer, Architect, Host). Three active states in the middle band (plan_drafting, plan_review, plan_revision). Two paused states below that (blocked_on_architect, paused_by_architect). Four terminal states along the bottom (plan_approved, max_rounds_exceeded, turn_timed_out, ended_by_architect). Edges are labeled with the action or event that fires the transition.

Click any node to see everything it touches: for a state, the transitions in and out of it plus the role that owns it; for a role, the states that role writes to.

Why these regions matter

  • Three active states + one revision loop — the plan bounces between plan_drafting/plan_revision (draftor) and plan_review (reviewer) until the reviewer approves or max_rounds is exhausted. This is the load-bearing debate cycle.
  • Two paused states, not one — blocked_on_architect is model-triggered (a stuck model calls escalate). paused_by_architect is human-triggered (the Architect calls pause). Same "wait for human unblock" shape, distinct origins so the residue tells you who paused it.
  • Four terminal states, three of them "unresolved" — only plan_approved ends with a plan the reviewer signed off on. max_rounds_exceeded, turn_timed_out, and ended_by_architect are all "loop stopped without approval" — the residue still tells you how far it got, but the plan isn't blessed.
  • The Host has exactly one write path — timeout enforcement. Everywhere else it's a reader of events.jsonl. That's the "Host Write Authority" TRIPWIRE in the charter; it's why turn_timed_out is the only terminal the Host reaches into.
  • Architect can reach every terminal-side state — unblock, pause, interject, end. The Architect role is intentionally the most powerful. Models can only submit, escalate, or wait.

Reading order

  1. Click Draftor — see the two active states the draftor writes to and how submit_draft connects them.
  2. Click plan_review — the highest-fan-out node in the graph. See the four transitions out of it (approve, findings, max-rounds, escalate/pause/end/timeout).
  3. Click blocked_on_architect — see the three active states that can enter it (via escalate) and the three active states unblock can restore to.
  4. Click plan_approved — the happy-path terminal. Reachable only from plan_review. Everything else is either "loop stopped early" or "loop never resolved".
  5. Click Host — see the single write path (turn_timed_out). Compare to Architect for the contrast.

Boundaries and tripwires

  • Stage-role consistency — plan_drafting and plan_revision require the draftor; plan_review requires the reviewer. advance_unblocked() enforces this on the restore path so unblock can't send the loop into an impossible state.
  • Escalate bypasses the turn check — either model role can escalate from any active state, even if it's not their turn. Intentional: a model stuck waiting for a submit that will never come needs the ability to break out.
  • Terminal states are terminal — no transitions out. The Architect cannot "un-approve" a plan or resurrect a timed-out loop. Start a new loop instead. This is why the residue directory is the durable record.
  • Session lock write ordering — every writer (submit, escalate, unblock, timeout) saves session.json before appending to events.jsonl, both inside the exclusive lock. Prevents the Host from observing a terminal event whose session state isn't yet durable.
  • Token nonce separation — tokens carry a secret nonce that lives only in gitignored .tokens.json. Committed session.json holds only role names. Tokens can't be reconstructed from git history.

Open questions

  • Should blocked_on_architect and paused_by_architect converge into a single "paused" state with a paused_by field, or is the distinct-state shape worth the extra state-machine surface? (Currently two states — kept distinct because the CLI validators branch on the state name.)
  • Dashboard integration is deferred (charter: "Does Not Own"). Whether the loop map surfaces in the Dashboard as a live view, or the Dashboard just links out to this blueprint, is an open UX call for the Blueprints 2.0 follow-on releases.
