Summary

Gator is a local, Git-native governance layer for AI-assisted engineering. It runs as one Python command (gator, installed with pipx, standard library only). It keeps its knowledge layer in each repository's .gator/ folder. It enforces its rules through Git hooks at commit time. The central idea is the charter: a committed map of a module's functions, callers and invariants. The agent reads the charter before it changes code and updates it with every change. The commit gate blocks a code change that has no charter change.

Around that core, Gator adds a local Dashboard for people, Gator Loop for governed multi-agent planning and coding, and an evidence trail (commit trailers and session snippets) for audit. Enterprise is an optional server that collects that evidence across machines. Git is the system of record. No hosted service is needed for the core product.

The system on one page

Gator has three places where it runs and stores data: the developer machine, each governed repository, and (optionally) an Enterprise server. The AI coding tool is not part of Gator. Gator works with Claude Code, Codex CLI and Gemini CLI through their hook interfaces and through the files that the agent reads.

Gator component Data in the repository External tool or machine state Optional (dashed border)
Figure 1. Gator's three locations. Every arrow is labeled or connects two named boxes. The Architect (the human owner) works through the AI CLI and the Dashboard.

Design decisions behind this shape

  • Git is the database. Governance state is files and commit trailers in the repository. It travels with every clone and needs no server.
  • No runtime dependencies. The base wheel uses only the Python standard library (Python 3.9–3.13). Only the Enterprise server needs FastAPI, SQLAlchemy and PostgreSQL.
  • Local enforcement. The commit gate is a Git hook. It is deterministic and runs no model.
  • Vendor-neutral. Gator never edits CLAUDE.md, AGENTS.md or GEMINI.md. The agent enters through gator init, which works with every vendor.

Where the code lives

The core product is one package, src/gator_command/. The CLI router (cli.py) maps each gator subcommand to one script in src/gator_command/scripts/. The scripts that run inside a governed repository at commit time are in src/gator_command/templates/gator-starter/scripts/. Enterprise is separate, under enterprise/.

Why scripts, not a normal package

Most modules are standalone scripts loaded by file path, not imports inside one package. This is deliberate: copies of the commit-time scripts run inside governed repositories, where the installed package may be missing. The cost is extra copies of some files (package, starter template, Enterprise bundle). Byte-identity tests keep most copies in step. Issue #91 tracks the copies that have drifted.

Feature 1 — Governed sessions

A governed session starts when an AI agent opens in a governed repository. Gator records the session and gives the agent a fixed reading order. The agent then works charter-first.

AI CLI startsvendor tool
hook
Session hookrecords the session
gator initchecks hooks · registers repo
Opening readsGATOR_INIT · constitution · mission
Chartersvia INDEX.md
  1. Session capture. The vendor's SessionStart hook calls gator hook session-start. It records which vendor, model and session are active, so later commits can name them. It never blocks the session.
  2. Boot check. gator init checks and repairs the Git hooks, registers the repository with the Dashboard, and prints the files to read in order.
  3. Orientation. The agent reads GATOR_INIT.md, the constitution (the rules), then mission, roadmap and inbox.
  4. Charter-first work. Before a code change, the agent finds the charter through charters/INDEX.md. After each edited file, the agent updates that charter.

Feature 2 — The commit gate

The commit gate is Gator's enforcement point. Three Git hooks run one script, gator-pre-commit.py, in three phases. The gate is deterministic and makes no model calls.

Gator step Blocked (thick border, labeled BLOCKED) Done (thick border, ✓)
Figure 3. One commit through the gate. Phases 1–3 are the same script with --phase validate, trailers and cleanup.

What each phase does

  1. Validate (pre-commit). Blocks when code changed but no charter changed, when commit_draft.md is not filled in, or when a blocking lint rule fires. It writes the reason to whiteboard.md and the state to status.json.
  2. Approval path. Only the Architect can approve a blocked commit. The approval is bound to a SHA-256 hash of the exact staged change. Any restage makes the approval invalid. It is consumed only after the commit exists.
  3. Trailers (commit-msg). Builds the message from commit_draft.md and appends Gator-* trailers: change type, significance, agent, Architect, charter-changed flag, and any override.
  4. Cleanup (post-commit). Resets the draft, retires the approval, and writes one session snippet (.gator/session-snippets/*.json) for the evidence trail.

Feature 3 — Install, update and runtime selection

Gator ships as one wheel (pipx install gator-command). Three commands put it into a repository and keep it current. A runtime pin decides which copy of the commit-time scripts runs.

CommandWhat it doesMain code
gator gatorize <repo>First install: detects the scenario, copies the starter templates into .gator/, installs hooks, sets ignore rules, registers the repository with the Dashboard.gatorize.py, gatorize/
gator updatePlans first (read-only), then refreshes templates and hooks. Migrates older layouts only when asked.gator-update.py, gator_layout.py
gator initSession boot. Repairs stale hooks without blocking.gator-init.py

Runtime pin. .gator/runtime-pin.json records the Gator version and a SHA-256 manifest of the commit-time scripts. At commit time, gator_core.resolve_governed_runtime() compares the pin with the installed CLI:

SituationResult
Pin matches the installed CLIRuns the machine runtime
Installed CLI is newer than the pinRuns and advises gator update
Installed CLI is too old for the pinRefuses and tells the user to upgrade
Pin is corrupt or unreadableFalls back to the repository's own scripts. A broken pin never blocks commits.
Branch has no .gator/Warns and allows the commit

Feature 4 — The Dashboard

The Dashboard is the human view of Gator. gator dashboard starts a local HTTP server that listens only on 127.0.0.1. It serves a plain JavaScript single-page app (no framework, no build step). It reads the registered repositories and their Git history. It writes only through specific actions: Loop commands, update and gatorize.

Browser viewsWelcome · Fleet · Repo · Commits · Loop · Docs
HTTP (loopback)
Routesgator-dashboard.py
Adapters + content policydashboard/data.py · content_policy.py
Repositories + Loopfiles · git · loop/host.py
  • Containment. Every file request is checked against the repository root. The check rejects symbolic links and Windows directory junctions. Served HTML gets a strict Content-Security-Policy.
  • Concurrency. The server is threaded, so a slow listing does not block other requests. Dashboard locks are never held while a Loop lock is taken. The Loop locks stay the only authority for Loop state.
  • Offline snapshot. dashboard/snapshot.py builds one self-contained HTML file that needs no server. It holds the summary data only; the Repo view is off in a snapshot.

Feature 5 — Gator Loop

Gator Loop runs a governed exchange between two AI agents: a Draftor writes, and a Reviewer checks. The Architect controls the loop. The agents can be from different vendors, for example Claude as Draftor and Codex as Reviewer. Each agent joins with its own token. Gator checks the token, the role and whose turn it is on every command.

Active stage Approved (thick border, ✓) Human control
Figure 4. One loop round. Planning mode uses plan_* stages; coding mode uses implementation_* stages.

Two modes

  • Planning loop. The Draftor writes a plan from the Architect's sketch. The Reviewer approves it or requests changes. The output is an approved plan.
  • Coding loop. The Draftor implements an approved plan, one checkpoint at a time. At each submission, Gator records a Git snapshot (tree and HEAD) of the candidate, so the Reviewer approves exact code. After approval, the loop reports whether that tree was committed.

How it is built

All loop state is in .gator/loops/<loop-id>/: session.json (the current state), events.jsonl (an append-only log), and round-numbered artifacts (plans, findings, approvals). Operating-system file locks serialize every change. The modules form a strict layering with no import cycles:

sessionstate · tokens · locks
events · state_machinelog · legal transitions
submit · liveness · gitsnapturns · waiting · Git snapshot
hoststart · watch · extend
cligator loop …

Each module depends only on the modules to its left. The Dashboard reads loop state through session and events, and changes it only through host. gator loop codex is an opt-in launcher. It prepares an isolated Codex profile that allows only the routine loop commands.

Feature 6 — Evidence, audit and fleet

Gator produces evidence as a side effect of normal work. All of it is in Git, so every clone carries it.

Commit trailersGator-* on every commit
Session snippets.gator/session-snippets/*.json
Aggregationgator-session-aggregator · gator-audit
ViewsCommits · Audit · pulse · fleet report
QuestionAnswered by
Which agent and model made this change, and under which Architect?Commit trailers (Gator-Agent, Gator-Architect, …), shown in the Dashboard Commits view

Enforcer review is a separate, optional check. On the Architect's request, gator hook enforcer-review sends the diff and the matching charters to a different model. The findings go to whiteboard.md for the Architect to decide. The enforcer never edits code.

Feature 7 — Enterprise (optional)

Enterprise collects governance evidence across many machines and repositories. It is a separate install. The base wheel contains only a small dispatcher (gator enterprise) and does not import Enterprise code.

enterprise-cliactivate · sync · transcripts pull
HTTPS + token
Enterprise APIFastAPI · auth · tenants
PostgreSQL + blob storeevidence · policy · raw transcripts
Audit answerswhich transcripts made this commit
  • Transcript custody. The CLI uploads Claude, Codex and Gemini session transcripts. The server keeps the raw transcript as the source of truth and links it to commits and machines.
  • Policy. The organization publishes hook policy and standards. Machines pull them with gator enterprise sync.
  • Current limit. The Enterprise CLI installs only from a source checkout. A single pipx install path is the open blocker for a public Enterprise release.

Trust boundaries and failure policy

Gator chooses deliberately between failing open (allow and warn) and failing closed (refuse). The rule: never let a Gator fault stop normal Git work, and never silently weaken a control that a person set.

ConditionBehaviorReason
Code change without a charter changeBlockCore rule. Only an Architect approval of the exact staged tree releases it.
Corrupt runtime pinAllow with the repository's scriptsA broken pin must not stop commits.
Malformed user preference fileRefuseA fallback would silently override what the user set.
Invalid Enterprise activationNot activatedRefusing a feature is safe; refusing a commit is not.
Session hooks failSession continuesCapture is best effort; it never blocks the agent.
Dashboard request outside a repository rootRejectContainment checks symlinks and junctions.
Loop command with the wrong token, role or turnRejectOnly the Architect token can pause, end, extend or reopen.
Unknown permission rule in the Codex loop profileRefuse to launchGator does not overwrite a rule it did not write (see #87).

Architecture health

A code assessment on 2026-10-23 found clean module boundaries in the Loop package and a narrow seam between the Dashboard and the Loop. It also found these maintenance risks. Each one has an issue.

RiskImpactIssue
The charter verifier ignores globs in charter coverage lines, so most of its 157 coverage warnings are false.Real charter drift is hidden in noise. Drift detection is the core product claim.#88
gator-dashboard.py is 4,600 lines; one handler class is 2,600.Every Dashboard change touches one large file.#89
views/loop.js is 4,400 lines.Slow to change; the Paper redesign is the time to split it.#90
Some copied scripts have drifted (for example gator_core.py in the Enterprise bundle).Enterprise-provisioned repositories may miss newer commit-gate rules.#91
Modules import each other's private names; several Loop modules are 1,100–1,900 lines.Hidden coupling; refactors break in unexpected places.#92, #93

Key point

Test code is about the same size as product code (about 48k lines), and contract tests pin the shared formats. Most risk is in the size of a few files, not in the design. The highest-value fix is #88, because it makes charter drift visible again.
