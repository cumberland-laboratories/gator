Summary

Enterprise has two independently-installable pieces: a FastAPI server (source checkout under enterprise/app/, deployed to Fly.io or run locally) and an operator CLI (enterprise/enterprise-cli/, installed alongside base Gator on each developer machine). You bring up the server first, bootstrap an admin token, hand that token to a developer machine, run gator enterprise activate, then gator enterprise repo init per repo you want under Enterprise governance. First-commit verification confirms the whole pipe works end-to-end. Expect an hour for the first machine + first repo once the server is up; subsequent machines and repos are minutes.

The whole pipeline at a glance

Server up Fly.io or local
bootstrap
Admin token issued once
activate
Machine ready ~/.gator/
repo init
Repo governed .gator/

Four phases, six commands total (server bring-up plus four on the developer side). Every phase leaves durable state on disk you can inspect, so partial progress is always recoverable.

Before you start

Confirm each of these before spinning up the server. Missing any of them will show up as a confusing failure later.

Prerequisite Where you need it How to get it
Python 3.11+ Server host AND every developer machine python.org, package manager, or Microsoft Store (not just the Windows App Execution Alias — that trips the wrapper resolver).
Git Every developer machine Standard install. On Windows, prefer Git for Windows with Git Bash.
Base gator-command Every developer machine pipx install gator-command. Confirm with gator --version.
Source checkout of the Gator monorepo Server host AND every developer machine that will run enterprise-cli git clone the monorepo. Enterprise pieces are source-checkout-only today.
A hosting decision Server side Fly.io (documented, has fly.toml) or run locally under uvicorn. Anything else works if it can host a Python web app + Postgres, but you are on your own for deploy config.
PostgreSQL access Server side Fly Postgres via fly postgres create, or any Postgres URL you can reach from the server host.
flyctl installed and authenticated (Fly path only) Wherever you deploy from Fly install docs. Then fly auth login.
Windows caveat — python resolution

Windows ships a stub python3 App Execution Alias that passes command -v but exits non-zero when invoked. The Enterprise hook wrappers probe every candidate with -V before accepting it, so a machine with only the stub fails loudly at activate with a clear message. Install a real Python (from python.org or the Microsoft Store, not just the alias) before running gator enterprise activate.

Choose a deployment path

Path When to use What you get
A. Fly.io Documented Multi-machine team, evaluators outside your local network, anything that outlives your laptop. Persistent HTTPS URL, managed Postgres, one-command redeploys, migrations on every deploy.
B. Local development Fast iteration Kicking the tires solo, integration testing, air-gapped experiments. Runs on localhost. You manage Postgres. Only reachable from your machine unless you tunnel.
Both paths are supported

The enterprise/README.md covers both. The rest of this guide walks through each in its own section — skip the one you are not using.

Path A: Fly.io deployment

From a source checkout of the monorepo, cd enterprise. All commands below assume that working directory.

  1. Create the Fly app

    Pick a name unique across Fly.io. The included fly.toml uses gator-enterprise-dev; clone the file and rename for staging or prod.

    fly apps create gator-enterprise-dev

  2. Create and attach Postgres

    Fly Postgres in the same region as the app. Attach sets DATABASE_URL as a Fly secret automatically — no manual secret setup for E1.

    fly postgres create --name gator-enterprise-dev-db --region iad
fly postgres attach gator-enterprise-dev-db -a gator-enterprise-dev

  3. Deploy

    Builds the container from Dockerfile, runs Alembic migrations via the release_command in fly.toml, starts the API + worker processes.

    fly deploy

  4. Verify the server is up

    Health endpoint should return HTTP 200 with no auth required.

    curl https://gator-enterprise-dev.fly.dev/healthz
What is running now

Two processes: api (gunicorn + uvicorn workers on port 8000, TLS-terminated by Fly on 443) and worker (background poller of the ingest_jobs table). Migrations ran once at deploy time. Every subsequent fly deploy re-runs migrations then rolls the containers.

Path B: Local development server

From a source checkout, cd enterprise. You need a Postgres reachable from your machine — either a local install, a Docker container, or a proxied Fly Postgres.

  1. Install server deps

    pip install -r requirements.txt

  2. Point at your database

    Set DATABASE_URL. Standard libpq format. For a Fly Postgres via proxy, use the URL fly proxy prints.

    export DATABASE_URL="postgresql://user:pass@localhost:5432/gator_enterprise"

  3. Run migrations

    alembic upgrade head

  4. Start the API

    --reload is helpful for local development. Drop it in anything resembling production.

    uvicorn app.main:app --reload --port 8000

  5. Start the worker (separate terminal)

    python -m app.worker

  6. Verify

    curl http://localhost:8000/healthz
Local server, remote machines

A local server only accepts connections from your machine unless you tunnel or expose it. For evaluating with a second machine or another user, either use the Fly path or set up a tunnel (ngrok, cloudflared, ssh -R) explicitly. Do not paste the plain localhost:8000 URL into another machine and expect it to work.

Bootstrap the admin token

The first admin token is generated on the server host, printed to stdout, and never persisted retrievably. Copy it immediately to a secrets manager — you cannot get it back.

Single-shot output

The bootstrap command prints the token once. If you lose the terminal output before saving it, you cannot recover the token — you have to run bootstrap again to issue a new one. Have your paste target open before running the command.

On Fly.io

fly ssh console -a gator-enterprise-dev -C "python -m app.admin bootstrap"

Local

From the same shell where DATABASE_URL is set:

python -m app.admin bootstrap

Confirm it works

Use the token to hit the “whoami” endpoint. Should return a small JSON payload identifying the token.

curl -H "Authorization: Bearer <paste-token-here>" \
  https://gator-enterprise-dev.fly.dev/api/v1/tokens/me

Install the enterprise-cli package

The base wheel (pipx install gator-command) ships only the thin gator enterprise dispatcher. Without the enterprise-cli package installed, every gator enterprise <verb> returns exit code 69 with sentinel [gator-enterprise-unavailable]. Install the CLI on every developer machine that needs Enterprise capability.

From a source checkout on the developer machine:

pipx inject gator-command ./enterprise/enterprise-cli/
Why pipx inject

Base Gator is installed via pipx into an isolated venv. pipx inject installs the enterprise-cli package into that same venv, so the dispatcher can import it. A plain pip install would go into your system Python and the dispatcher would not see it. Alternate approaches (pipx install ./enterprise/enterprise-cli/ as a second app) work but leave the base dispatcher unable to delegate.

Verify:

gator enterprise --help

Should list every advertised verb. If any verb still returns exit 69 after this step, the inject did not land — check with pipx list and confirm gator_enterprise_cli shows under the gator-command venv.

Activate the developer machine

One-time machine setup. Creates ~/.gator/enterprise/, installs global git hooks under ~/.gator/hooks/, points git at them via core.hooksPath, writes machine identity + keypair, registers the machine with the server, and runs sync to pull down initial policy.

gator enterprise activate \
  --server-url https://gator-enterprise-dev.fly.dev \
  --token <paste-admin-token>
Global hook install

activate sets git config --global core.hooksPath ~/.gator/hooks. That is machine-wide: every repo on the machine will now dispatch to Enterprise hook wrappers. The wrappers no-op on ungoverned repos (they check for .gator/repo-id and exit cleanly if absent) so this does not break unrelated projects, but be aware you are making a machine-scoped change.

What lands on disk after this step:

~/.gator/
  machine-id
  hooks/
    pre-commit
    commit-msg
    post-commit
  enterprise/
    config.json              # server URL + activation timestamp
    hook-policy.json         # local mode cache (empty until repo init)
    crypto-policy.json
    credentials.json         # chmod 600, contains the API bearer
    keys/machine-private-key.pem
    keys/machine-public-key.pem
    policies/                # cached org policies
    org-keys/

Confirm the machine is registered with the server:

gator enterprise status
Idempotent

activate is safe to re-run. --force redeploys the hook wrappers after a source-side wrapper change without rotating the machine keypair or wiping the hook-policy cache. Use --regenerate-keys only when you intentionally want a fresh keypair (rare — that invalidates every previously-encrypted session block on this machine).

Provision your first repo

Per repo you want under Enterprise governance. Run from the repo root, or pass the path as the first positional argument.

cd /path/to/your-repo
gator enterprise repo init . --mode strict

What this does, in order:

  1. Verifies the target has a .git/ directory.
  2. Derives a canonical repo identifier from git remote origin (SSH and HTTPS forms are normalized to the same canonical form).
  3. Writes .gator/repo-id with the canonical identifier.
  4. Copies the bundled hook + session-capture scripts into .gator/scripts/.
  5. Creates CLAUDE.md and AGENTS.md if missing (agent entry files pointing to org + repo policy).
  6. Writes the requested mode locally to ~/.gator/enterprise/hook-policy.json, keyed by the canonical id — so the wrapper honors the mode even if the server does not yet know about this repo.
  7. Attempts server-side registration of the hook mode (best-effort — no-ops silently for repos the server does not know yet, which is fine).
  8. Runs sync so the local cache picks up any resulting server-side policy.
  9. Auto-stages the newly provisioned files with git add.

Choosing a mode

strict is the default and the right choice for most repos. See the capability guide for the full off / evidence_only / warning / strict comparison. In brief:

Mode Missing commit_draft Best for
strict defaultBlocksAny repo where the human or bot should explain the commit.
warningWarns, proceedsCI or bot repos that cannot interactively respond.
evidence_onlySilent, proceedsExplicit low-ceremony repos.
offSilent, proceeds, no evidenceEffectively disable Enterprise for this repo without disconnecting.
Repo-init self-repair

Re-running repo init on a repo that already has partial provisioning fixes what is missing without wiping what already works. The mode-write is a merge into hook-policy.json, not a replace. If a sync happens after you write a local mode, the sync merges server-wins-on-conflict; local-only entries survive.

Verify the evidence pipe

Nothing proves the whole chain works like a real commit + a real transcripts pull.

  1. Make a small commit in the provisioned repo

    Any non-trivial edit. If you provisioned in strict mode, you need a .gator/commit_draft.md with a body; otherwise the pre-commit hook will block.

    echo "test" >> README.md
echo "message: Test commit under Enterprise" > .gator/commit_draft.md
git add . && git commit -m "Enterprise verification test"

    You should see the base-Gator pre-commit output plus the Enterprise wrapper picking up the repo-id and dispatching. No block, no error — commit lands.

  2. Confirm the snippet was written

    Base Gator writes a session snippet for every commit. Check that one landed:

    ls .gator/session-snippets/ | tail -3

  3. Pull transcripts to the server

    Discovers vendor session files (Claude Code, Codex, etc.), uploads them to the server, records the machine attribution.

    gator enterprise transcripts pull

  4. Confirm the server sees your commit

    Query the commits list for the repo. Should include the SHA of the commit you just made.

    gator enterprise commits list --repo <canonical-id-from-repo-id-file>
If this all works

The pipe is live end-to-end: developer machine ↔ repo hook wrapper ↔ machine-local cache ↔ server ↔ database. Every subsequent commit under this repo flows through the same path automatically. The evidence flow (transcripts pull) is operator-triggered — run it on whatever cadence fits your governance policy: manually, cron, CI, or a scheduled job on the server host itself.

Where you go from here

With the pipe live, the natural next moves:

  • Second developer machine — on a fresh machine, run steps 8-9-10 (install enterprise-cli, activate with the same server URL and a token issued for that person, provision the same or a different repo). No server-side work needed.
  • Additional repos — run gator enterprise repo init per repo. Each gets its own canonical id and its own mode entry.
  • Issue per-user tokens — the bootstrap token is an admin token. For team use, issue narrower tokens via gator enterprise auth (see the server-side subcommand surface).
  • Provider integrations — wire GitHub or GitLab under gator enterprise providers so the server can enrich commit data with PR context and branch info.
  • Scheduled transcripts pull — put gator enterprise transcripts pull on a cron or CI schedule so evidence flows without manual runs.
  • Fleet reporting — gator enterprise reports for cross-machine and cross-repo visibility once you have >1 machine or >1 repo enrolled.
Aspirational reality check

Per Architect direction, Enterprise integration is explicitly deferred — some surfaces above (fleet reports, provider integrations at scale) are wired but not battle-tested. If you hit rough edges, they are known rough edges; log them and expect them to smooth out as the surface hardens. Base-wheel releases do not wait on Enterprise green tests.

Common problems

Symptom Cause Fix
gator enterprise --help shows the verbs but every verb returns exit 69 with [gator-enterprise-unavailable] The enterprise-cli package is not importable from the base-Gator venv. Run pipx inject gator-command ./enterprise/enterprise-cli/. Confirm with pipx list.
fly deploy fails at release_command with an Alembic error Migration chain conflict or missing revision. Check enterprise/migrations/versions/ for gaps. Run alembic history locally against the same DB URL to see the actual state. Re-deploy after fixing.
activate fails with a Python-resolver error on Windows Only the Windows App Execution Alias for python3 is on PATH; no real Python. Install a real Python (python.org or Microsoft Store). Re-run activate. The wrapper probes candidates with -V before accepting them.
Commit runs in strict even though you ran repo init --mode evidence_only On machines activated before the 2026-08-06 fix arc, the mode-lookup shell-interpolated $HOME, which broke on Git Bash for Windows. Wrapper fell through to strict. Run gator enterprise activate --force to redeploy the fixed wrapper. Machines activated after 2026-08-06 are unaffected.
transcripts pull reports zero transcripts uploaded No vendor session files under the discovery paths (Claude Code’s ~/.claude/projects/, Codex’s equivalent, etc.), or the session files are older than any recorded commit. Make a fresh commit from inside an AI session, then re-run transcripts pull. Discovery is time-scoped to recent commits.
Bootstrap token lost before saving Terminal buffer overrun, closed the window, whatever. Run python -m app.admin bootstrap again. Issues a new token. Old token is not automatically revoked — if the old one might be in a bad actor’s hands, revoke explicitly via gator enterprise auth.
Second machine cannot reach the local dev server Local server listens on localhost only. Not exposed to your LAN, let alone the internet. Either use the Fly path, or set up a tunnel (ngrok, cloudflared, ssh -R). Do not paste your local URL into another machine and expect it to work.
