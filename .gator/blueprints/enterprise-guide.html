Summary

Enterprise is an optional layer on top of base Gator. Base Gator works standalone on a single machine with one developer; Enterprise adds cross-machine and cross-repo governance: a control plane that owns policy, credentials it can revoke, hook modes an operator can dial per repo, and evidence custody (transcripts) that lives in Enterprise-managed storage rather than in Git. The base install (pipx install gator-command) ships only a thin gator enterprise dispatcher; the real command bodies live in the source-checkout enterprise/enterprise-cli/ package and the FastAPI service under enterprise/app/. Both are explicitly aspirational — the Architect direction is "the enterprise portions do not need to work right now" — so most fleet-scale features are wired but not required for base-wheel releases.

The three scopes

Enterprise’s configuration lives in three distinct places, on purpose. Every design decision hinges on which scope owns what.

Repo .gator/
Scope Owns Never owns
Server
enterprise/app/		 API auth, provider integrations, repo inventory, hook-policy authority, org policy documents, machine-key registry, org encryption keys, evidence indexing, drift evaluation, fleet reports. Anything a machine or repo owns locally — the server doesn’t reach into a machine at commit time.
Machine
~/.gator/		 Credentials, machine identity, hook-policy cache, org-policy cache, crypto-policy cache, global git-hook wrappers (via core.hooksPath), machine keypair (if crypto is on). Repo identity or repo-scoped policy — those come from the repo it’s currently inside.
Repo
.gator/		 Repo identity (repo-id), org-policy pointer, bundled repo-local scripts, evidence landing zones, agent entry files (CLAUDE.md / AGENTS.md). Credentials, machine private keys, hook-policy authority — those stay off-repo permanently.
Why this split matters

Commit-time behavior is deliberately mostly-local. The global hook wrapper reads the machine’s cached hook-policy at every commit — it does not call the server. Server availability at commit time is a nice-to-have, not a load-bearing requirement. Policy changes propagate on the next sync; hook mode never depends on server reachability.

Activation, sync, repo provisioning

Three phases, conceptually. In practice activate calls sync at the end and repo init triggers another sync, so the operator usually types two commands, not three.

  1. gator enterprise activate

    One-time machine setup. Creates ~/.gator/enterprise/, installs global git hooks under ~/.gator/hooks/, sets git config --global core.hooksPath, writes machine identity + keypair (crypto), registers the machine with the server, calls sync at the end.

    gator enterprise activate

  2. gator enterprise sync (usually implicit)

    Refresh machine-local caches from the server: hook policy, org policy documents, crypto policy, org public key. The wrappers rely on these caches at commit time. Called automatically at the end of activate and at the end of repo init. Run manually when the operator knows the server has new policy.

    gator enterprise sync

  3. gator enterprise repo init <path>

    Provision a specific repo. Writes .gator/repo-id (derived from git remote origin if not supplied), copies the bundled hook + session scripts into .gator/scripts/, creates evidence landing zones, creates agent entry files, and writes the requested hook mode locally so the wrapper honors it even if the server hasn’t heard of the repo yet.

    gator enterprise repo init . --mode strict

  4. Everything after that is normal git

    Commit as usual. The global hook wrapper fires, reads the repo’s canonical id, looks up the hook mode in the local policy cache, and dispatches to the repo-local .gator/scripts/gator-pre-commit.py. Nothing else operator-facing changes.

Warning — --force semantics

activate --force is safe for redeploying hook wrappers after a source change. It does not rotate the machine keypair (that’s --regenerate-keys) and does not wipe the hook-policy cache (locally-written repo-init intent-modes survive). Rotating the keypair on every wrapper redeploy would invalidate every previously-encrypted session block and desync the server’s registered public key. Regression pins live at enterprise/tests/test_activate_hooks.py::TestActivateKeyPreservation.

Hook modes: off / evidence_only / warning / strict

Every governed commit runs in one of four modes. The mode determines whether missing evidence (a commit_draft.md) blocks the commit, downgrades to a warning, still records evidence silently, or does nothing.

Mode Missing commit_draft Evidence captured When to use
strict Default BLOCKS the commit Yes Any repo where a human/bot should be able to explain the commit. Per Architect direction 2026-08-07: this is the default because commits shouldn’t go silently.
warning Prints warning, commit proceeds Yes CI or bot repos that can’t interactively respond to a block. Explicit opt-in only.
evidence_only Silent, commit proceeds Yes Deliberate low-ceremony repos where evidence still flows but the enforcement gate is disabled.
off Silent, commit proceeds No Effectively disable Enterprise governance for this repo without disconnecting. Rare.
Where the mode lives

The mode is stored in ~/.gator/enterprise/hook-policy.json, keyed by the repo’s canonical identifier. Set locally by repo init --mode <X>. Server-side registration overlays on top when the sync runs, with the merge rule: server wins on overlapping keys, local-only entries survive. That means a freshly-provisioned repo the server doesn’t know about yet still runs in the requested mode — the sync doesn’t wipe the local intent.

Fail-safe default

Any exception during mode lookup (missing policy file, malformed JSON, missing env var, path resolution failure) falls through to strict. This is intentional — a broken policy state must not relax enforcement below the strictest option. Consequence: if hook-policy.json is corrupted, every commit runs in strict until the operator restores it.

Evidence flow (transcripts-first)

Post-2026-08-08 the evidence path is transcripts-first. This is the biggest change from the historical enterprise-configuration.md shape.

commit .gator/session-snippets/
operator triggers
transcripts pull enterprise-cli
POST /ingest
server storage DB + blob

What changed vs. the historical model:

  • Per-commit session-block generation retired from the post-commit hook (2026-08-09). The hook no longer runs a block generator on every commit; it just cleans up.
  • Evidence flows on operator schedule, not commit schedule. The operator (or a scheduled job) runs gator enterprise transcripts pull, which discovers vendor session files (Claude Code, Codex, etc.), uploads them to the server via POST /api/v1/transcripts/ingest, and records the machine attribution trailer.
  • .gator/session-blocks/ stays gitignored globally. The historical design committed evidence to Git; the current design keeps evidence in Enterprise-managed storage and Git in the repo.
  • Session snippets still flow at commit time — the base-Gator pre-commit hook writes a .gator/session-snippets/<date>.json entry per commit. Snippets are lightweight commit-time evidence; transcripts are the fuller after-the-fact record.
What this means for the Architect

Nothing changes at commit time. The change is entirely on the evidence-ingest side: instead of the post-commit hook doing crypto and writing artifacts, the operator (or a cron) runs transcripts pull when it’s time to update the server. Base Gator hooks stay lightweight; Enterprise handles the fuller custody chain.

Subcommand surface

Base install lists every verb via gator enterprise --help. Without the enterprise-cli package, every verb returns EX_UNAVAILABLE = 69 with a stable sentinel [gator-enterprise-unavailable]. With it, delegation is transparent.

Client-side (developer / repo operator)

Verb What it does
activateOne-time machine setup. Installs global hooks, generates machine keypair, registers with server, runs sync.
syncRefresh machine-local caches (hook policy, org policy, crypto policy) from the server.
repoProvision or reconfigure a repo. repo init <path> --mode <X> is the common form.
transcriptsDiscover local vendor session files and upload them to the server. The transcripts-first evidence path.
commitsQuery the server for commit records tied to this machine or repo. Read-side of the ingest pipe.

Server-side (operator / admin)

Verb What it does
authAPI-token management. Issue, list, revoke.
reposServer-side repo inventory. List, query, reconcile.
providersProvider integrations (GitHub, GitLab, etc.).
policiesOrg policy documents. CRUD on the source-of-truth surface.
reportsFleet-scale reporting. Drift, activity, evidence coverage.
machinesMachine registry — the machines that have activated.
blocksLegacy session-block operations. Historical; transcripts-first is the current path.
Verb-mapping guard

The base-wheel dispatcher carries a frozenset (ENTERPRISE_CLI_VERBS) of what the enterprise-cli package actually handles. Every advertised verb must be in that set; a mismatch surfaces as a contributor-error guard rather than a runtime failure. Adding or removing a verb in enterprise-cli requires updating the dispatcher constant in the same commit. Regression pin: tests/test_gator_enterprise.py::TestConstants::test_every_advertised_verb_is_mapped.

Where state lives on disk

Machine (~/.gator/)

~/.gator/
  machine-id                             # stable machine identity
  hooks/                                 # global git hooks (activated core.hooksPath)
    pre-commit
    commit-msg
    post-commit
  enterprise/
    config.json                          # server URL + activation timestamp
    hook-policy.json                     # local mode cache, keyed by repo-id
    crypto-policy.json                   # crypto policy cache
    cli-python-path                      # pinned interpreter for enterprise-cli
    credentials.json                     # API bearer (chmod 600 on POSIX)
    policies/<slug>.md               # cached org policy documents
    org-keys/org-public-key.pem          # server-side org public key (crypto)
    keys/machine-private-key.pem         # never leaves this machine
    keys/machine-public-key.pem          # registered with server

Repo (.gator/)

.gator/
  repo-id                                # canonical repo identifier
  org-policy.md                          # pointer to org policy (repo-visible)
  scripts/                               # bundled hook + session-capture scripts
    gator-pre-commit.py
    gator-session-open.py
    ...
  session-snippets/                      # commit-time snippets (tracked)
  session-blocks/                        # gitignored under transcripts-first
CLAUDE.md                                # agent entry file (Claude Code)
AGENTS.md                                # agent entry file (Codex, Gemini, ...)
Clean separation

Secrets never enter the repo. Credentials, machine private keys, and cached policy all stay on the machine. The repo carries participation markers and repo-visible guidance for agents — nothing an attacker cloning the repo would find valuable.

Common gotchas

Symptom What’s actually happening Fix
Every gator enterprise <verb> returns exit 69 with [gator-enterprise-unavailable] The enterprise-cli package isn’t importable. Base install alone doesn’t include command bodies. Install the enterprise-cli package from source: pip install ./enterprise/enterprise-cli/. Or accept that base Gator is what you need and ignore Enterprise.
Windows commits run in strict no matter what repo init --mode requested Bug fixed 2026-08-06 — earlier hook wrappers shell-interpolated $HOME, which gave MSYS-form paths Windows Python couldn’t open. Wrapper caught the error and fell through to strict. Re-run gator enterprise activate --force on the machine to redeploy hooks with the fixed wrapper. Machines activated after 2026-08-06 aren’t affected.
Sync wipes a locally-set repo mode Would happen if _do_sync replaced instead of merged. It merges (server-wins on overlapping keys), so this shouldn’t happen — but if it did, the local intent-write on repo init is the guard. Re-run repo init --mode <X>. The mode is re-written locally before the sync fires.
Commit hook can’t find python on Windows Windows’s stock python3 App Execution Alias passes command -v but exits non-zero when actually invoked. Every hook probes candidates with -V before accepting them; a machine with only the alias fails with a clear stderr message. Install a real Python (from python.org or Microsoft Store, not just the alias) and re-run gator enterprise activate --force.
Post-commit hook makes no session blocks Retired 2026-08-09 as part of the transcripts-first pivot. This is intentional, not broken. Use gator enterprise transcripts pull for evidence ingest. Post-commit only runs cleanup now.

Integration status & what’s deferred

Aspirational-by-Architect-direction

Per the Architect: "the enterprise portions do not need to work right now ... we are not requiring it to work out of the gate." Base-wheel releases don’t wait on Enterprise green tests. enterprise/tests/ can be red without blocking a ship. Base CI (tests/ + contracts/compatibility/) is the release gate; Enterprise CI is scoped independently.

Concretely deferred:

  • Server deployment — the FastAPI service is source-checkout only. No hosted instance today.
  • Dashboard integration — the base-Gator Dashboard doesn’t surface Enterprise state (per-repo mode, transcript ingest status, etc.). Blueprints 2.0 Release C-adjacent territory.
  • Encryption roundtrip — migration 007 shipped the key columns; the client-side encryption path was scoped down when transcripts-first replaced the block-first design. Envelope-encryption code lives in enterprise/app/routes/crypto.py and is exercised by enterprise/tests/ but isn’t on the base-wheel release path.
  • Full audit surface — five canonical audit questions all technically answerable via the current CLI + API pair, but the fleet-scale reporting shape is still evolving (2026-08-14 Phase 2 tranche extended it; more coming).

Concretely working (per current release):

  • Base-wheel dispatcher with stable exit-code + sentinel contract.
  • Machine activation with hook install, keypair generation, machine-key registration, config write.
  • Local hook-policy cache with the merge-preserves-local rule.
  • All four hook modes with the strict-default + fail-safe-strict semantics.
  • Bundled scripts stay byte-identical with the shipped and template copies (regression pin: tests/test_multi_session.py::TestByteIdentityAcrossThreeCopies).
  • Windows-safe python resolver + mode lookup (2026-08-06 fix arc, regression pins in test_activate_hooks.py).
  • Transcripts-first pull path (client-side transcripts pull, server-side ingest endpoint, DB schema).
