Summary

A Gator Loop is a structured exchange between two AI agents. The Draftor writes; the Reviewer checks and approves or asks for changes. You, the Architect, start the loop, watch it, and can pause, redirect or end it at any time. The agents never talk to each other directly. Every step goes through the gator loop CLI, which checks each agent's token, role and turn, and records the step in .gator/loops/<loop-id>/.

Loops come in two kinds. A planning loop turns your sketch into an approved plan. A coding loop implements that plan, checkpoint by checkpoint, and the Reviewer approves the exact staged code. The loop never commits. You make one normal commit at the end, and the loop then shows Committed.

Who takes part

Three roles, three tokens. A token is the only key to a role. Gator prints all three when the loop starts. The Dashboard keeps them for you and builds the join prompt for each agent.

Keep the architect token to yourself

The architect token is the only key to pause, interject, unblock, extend, reopen and end. Never paste it into an agent session. An agent with only its own token cannot change another role's work or skip a turn.

Start a loop

Use the Dashboard (Loop → Create) or the CLI. Both take the same options. Only one loop can be active in a repository at a time; a second start is refused until the first one ends.

What you wantCLINotes
Plan from a sketchgator loop start --feature <slug> --sketch <file>The usual start. The Draftor goes first.
Have your own plan reviewed… --plan-file <file>The Reviewer goes first. Your plan is not approved until the Reviewer approves it.
Revise an approved plan… --revise-from <loop-id> --sketch <file>The old plan and its approval are copied as fixed baselines. The source loop does not change.
Implement an approved plan… --mode coding --from-loop <loop-id>The source must be an approved planning loop.
Give both agents guidance… --brief <file>Markdown, 32 KiB or less. Coding loops can keep or drop the plan's brief with --source-brief.
Change the round limit… --max-rounds NDefault 3. You can add rounds later with extend.
Change the attention interval… --attention-interval SECONDSDefault 300. See Watch the loop. --turn-timeout is an older alias.

A sketch is your scope. Write what you want, what is out of scope, and any decisions already made. With charters in place, a Draftor needs only a few minutes of research. If research takes much longer, the sketch is probably too broad or the code has no usable charter.

Bring the agents in

Open one AI session for each agent. In the Dashboard, copy the join prompt for the role and paste it into that session. In the CLI, copy the role's gator loop status --token … line from the start banner.

Paste the join promptone role per session
gator initif the agent is new to the repo
Loop protocolnamed by GATOR_INIT.md
gator loop statusrole, stage, whose turn
wait · act · submitrepeat until the loop ends
  • Claude Code: /loop-join <token> does the same in one step.
  • Codex: gator loop codex opens Codex in an isolated profile that allows only the routine loop commands without a prompt. It never handles the token; you still paste the join prompt.
  • Any other agent: the join prompt works on its own, because it tells the agent to run gator init first.

How an agent waits for its turn

Agents call gator loop wait --token <token> --max-seconds 45 in a cycle. The exit code tells the agent what to do:

Exit codeMeaningAgent action
0It is your turn.Act and submit.
3Still not your turn (also while the loop is paused or waiting for the Architect).Wait again with the same command.
2The loop has ended.Stop

One round, and how the Architect steps in

Planning loops use plan_* stages and coding loops use implementation_* stages. The shape is the same.

Active stage Approved (thick border, ✓) Waiting for the Architect (dashed border, ⏸)
Figure 3. An agent can escalate, and you can pause, from any active stage. Unblock returns the loop to the stage it left.
  • Escalation. An agent that needs a decision runs gator loop escalate --reason …, optionally with --file for a written decision request. The loop waits for you.
  • Your answer. unblock --message … or unblock --file … sends your answer to the agent that resumes. The other agent does not see it. --no-response closes the request on purpose without an answer.
  • Executive summaries. In new loops, every Draftor and Reviewer turn ends with one plain-English paragraph. The Dashboard timeline shows it on the turn.

Attention notices replace timeouts

If an agent's turn lasts longer than the attention interval (default 5 minutes), Gator records one notice for you on that turn. The agents never see it, and the loop keeps running. A slow agent no longer ends the loop.

Architect controls

Every control needs the architect token. The Dashboard offers the same controls as buttons and fills in the token for you.

CommandWhenEffect
pause --message …Any active stageStops the loop and saves the stage. Agents see your message.
interject --message …Any active stageSends guidance without stopping. The agent whose turn it is sees it; it clears when that agent submits.
unblock --message … | --file … | --no-responsePaused or waiting for youResumes at the saved stage. --stage and --next-role override it.
extend --rounds N --message …After the round limitAdds 1–20 rounds and resumes the Draftor.
reopen --message …After an approved coding loopSends the code back to the Draftor for revision, for example when the result is Stale.
end --reason …Any time before the endStops the loop for good. Nothing is approved.

All commands take the form gator loop <command> --token <architect-token> ….

Coding loops in detail

  1. Checkpoints come from the plan. The approved plan's ## Coding Checkpoints section lists numbered checkpoints, each with a Verify: line. The Dashboard lists them with a mark and a word for each state: ✓ approved, ● active, ○ not started.
  2. The Draftor stages, then submits. The Draftor makes the changes, stages them with git add, writes an implementation note, and runs submit-implementation --checkpoint cpN. Gator records a Git snapshot of the staged tree and HEAD.
  3. The Reviewer approves exact code. The review is bound to the snapshot. If the staged tree changes after submission, the approval does not cover the new code.
  4. Next checkpoint. An approval of a checkpoint that is not the last moves the loop to the next checkpoint. The approval of the last checkpoint approves the loop.
  5. You commit. Make one normal commit of the approved tree. The loop then reports Committed.

After approval: does the commit match?

The loop compares the approved tree with Git. It checks only the first commit after the approved HEAD on the current branch.

ResultMarkerMeaningWhat to do
Pending[..]Not committed yet; the staged tree is still the approved tree.Commit.
Committed[OK]The first commit after the approved HEAD carries the approved tree.Done.
Stale[!!]The staged tree changed, a different tree was committed, the history diverged, or HEAD is detached.Check what changed. Use reopen if the code needs another review.
Unknown[??]Git could not answer (for example, a permission error).Fix the Git problem and check again.
Caution

A commit hook that changes files makes the commit differ from the approved tree, so the loop reads Stale. That is by design: the loop proves that the reviewed code is the committed code.

How a loop ends

EndingWhat it meansWhat to do next
plan_approvedThe Reviewer approved the plan.Start a coding loop from it, or revise it with --revise-from.
implementation_approvedThe Reviewer approved the last checkpoint.Commit the approved tree. Use reopen if it reads Stale.
max_rounds_exceededThe round limit was reached without approval.Read the last plan and findings. extend to continue, or end it.
ended_by_architectYou ended the loop.Your reason is in the session record.
turn_timed_outOlder loops only: an agent missed a turn deadline.Start a new loop. New loops use attention notices instead.
The loop never commits

Nothing in a loop writes to Git history. The loop folder is safe to commit as evidence; the token secrets (.tokens.json) and the lock files are ignored by Git.

The loop folder

.gator/loops/<feature>-<timestamp>/
  session.json              current state: stage, round, turns, roles
  events.jsonl              append-only event log (one JSON line per event)
  sketch.md                 your sketch (planning loops)
  architect-plan.md         your plan (--plan-file loops)
  architect-brief.md        your brief (--brief)
  plan.round-N.md           each Draftor plan; plan.current.md is the latest
  findings.round-N.md       each Reviewer response; findings.current.md is the latest
  approved-plan.md          the plan a coding loop implements
  implementation.round-N.md each implementation note; implementation.current.md is the latest
  decision-request.*.md     escalations with a written request
  .tokens.json              token secrets (ignored by Git)
  session.lock, host.lock   file locks (ignored by Git)

What can go wrong

SymptomCauseFix
Start is refused: another loop is activeOnly one active loop per repository.Finish or end the other loop first (gator loop list).
"requires role 'draftor', got 'reviewer'"An agent has the wrong token.Give each session its own role's join prompt.
An agent edits loop files directlyIt skipped the protocol.Re-paste the join prompt. Only the CLI may write loop files.
An agent keeps escalatingThe sketch is ambiguous, or the code it touches has no usable charter.Answer with unblock --file. If it repeats, end the loop and sharpen the sketch.
Approved coding loop reads StaleThe code changed after approval, or a hook altered the commit.Inspect the difference; reopen if it needs review again.
gator loop codex refuses to launchThe rule file has content Gator cannot read or show safely, or a saved approval matches a protected command.Read the message. It names the approval by its position. Remove or narrow that prefix_rule line in rules/default.rules. Ordinary saved approvals are kept and listed.
