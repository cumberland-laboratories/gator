Summary

Gator loop is a CLI-mediated debate between two AI models under human oversight. You write a short sketch, run gator loop start, hand each model its role token, and watch. The loop runs on file-based handoffs — models submit artifacts through the CLI, never talk to each other directly. The Architect can watch, pause, interject a message without pausing, unblock stalls, or stop a loop cold. Every event is durable in .gator/loops/<loop-id>/; nothing gets Git-committed automatically.

Before you start

Four things you need before the loop is worth starting:

  1. A feature slug

    Short identifier, kebab-case. Example: dashboard-html-preview, session-block-recovery. Used in the loop ID and directory name.

  2. A sketch file

    Markdown file describing what you want built. This is the scope contract — models cannot exceed what the sketch describes. Can be brief (a few paragraphs) or detailed (a full design sketch); the draftor expands it into a plan. Save it anywhere in the repo.

  3. Two AI sessions

    One for the draftor, one for the reviewer. Claude Code, Codex CLI, Gemini CLI — anything that can run gator subcommands works. Different models are fine (often better — you want independent perspectives, not two copies of the same voice).

  4. A monitoring terminal

    The gator loop start process blocks until the loop is terminal. That terminal is your primary event stream. Leave it open for the duration.

Note

You do not need to prep the models in advance. Each model reads its role, the protocol, and the sketch as soon as it joins. The Architect's job is scope + supervision, not model briefing.

Launching the loop

From the repo root, in your monitoring terminal:

gator loop start --feature dashboard-html-preview --sketch path/to/sketch.md

Common options:

Flag Default Purpose
--max-rounds N 3 Revision cycles before the loop stops with max_rounds_exceeded. Increase for complex plans; decrease for tight sketches.
--turn-timeout SECONDS 300 Seconds a model has to submit before the host fires turn_timed_out. Bump higher if models are slow to respond.

The host prints a banner with three tokens (draftor, reviewer, architect) and enters watch mode:

  gator loop

  Loop: dashboard-html-preview-2026-09-03T14-30-00Z
  Feature: dashboard-html-preview
  Max rounds: 3
  Turn timeout: 5m

  -- Tokens ------------------------------------------------

  DRAFTOR:
    gator loop status --token glp_ZGFzaGJv...

  REVIEWER:
    gator loop status --token glp_ZGFzaGJv...

  ARCHITECT:
    gator loop status --token glp_ZGFzaGJv...

  -- Watching -----------------------------------------------

  [14:30:01] loop started
  next: draftor (plan_drafting)
  waiting...
Warning

The three tokens are the entire access-control system. The architect token in particular is what gates pause, interject, unblock, and end. Never paste the architect token into a model session — that's the whole point of role separation. Keep it in a separate terminal or a note.

Orienting the models

Open a second (draftor) and third (reviewer) terminal. Give each model its role token. Two entry points:

Claude Code — slash command

/loop-join glp_ZGFzaGJv...

Any other AI (Codex, Gemini, etc.) — orientation prompt

I'm giving you a gator loop token. Follow the "gator loop join" instructions
in your entry point. Your token is: glp_ZGFzaGJv...

Each model then:

  1. Reads procedures/gator-loop-protocol.md — the behavioral contract.
  2. Runs gator loop status --token <token> — sees its role and whether it's its turn.
  3. Reads the sketch and any prior turn artifact (draftor reads sketch.md; reviewer also reads plan.current.md).
  4. Writes a submission and submits via gator loop submit-draft or gator loop submit-review.
Confirmed shape

The entire orientation is in the vendor entry-point file (CLAUDE.md, AGENTS.md, GEMINI.md). If a model reads its entry point, it knows exactly what to do with the token. If it doesn't, the token is inert — the model can't accidentally do damage because every write goes through gator loop.

Watching the loop run

Five surfaces, all read-only from the Architect's perspective. Pick the one that fits what you're trying to see.

Surface Best for Kind
The host terminal (gator loop start's stdout) Real-time event stream while the loop runs. Primary monitoring surface. Stream
gator loop tail --loop <id> Same event stream in a different terminal — useful when the host is backgrounded or you're on another machine. Stream
gator loop status --token <architect-token> Snapshot: current state, both models' join status, turn history, allowed commands. --json for machine reads. Snapshot
gator loop list Every loop this machine knows about — stage, round, whether blocked. For "which of my loops need attention?" Snapshot
Reading files in .gator/loops/<id>/ directly Any editor, cat, tail -f. All state is on disk — no hidden API. Direct
Why this works

The host is a reader of events.jsonl (with one write exception: timeout enforcement, protected by an exclusive file lock). There's no privileged "host view" vs. "Architect view" — they see the same event stream, observed at different times. Anything you build around the file surface stays in sync automatically.

What the loop directory contains

File Contents
session.jsonFull session state: stage, round, turn history, deadlines, resume state.
events.jsonlAppend-only event log. One JSON line per event.
sketch.mdThe original scope document (copied at gator loop start).
plan.current.mdLatest draftor submission — the plan under review.
findings.current.mdLatest reviewer submission — findings or approval body.
.tokens.jsonGitignored. Holds the secret nonces used to validate role tokens.

Architect controls

Four Architect-only commands. All require the architect token.

Active state running
pause
paused_by_architect deadline frozen
unblock
Active state resumed

pause

Freeze a running loop from any active state. Deadline stops counting. Saves the resume state so you can pick up exactly where you left off.

gator loop pause --token <architect-token> --message "Stopping for the day"

interject

Inject guidance without pausing. Message shown in the next gator loop status the active model runs; cleared when they submit. No state change, no deadline change.

gator loop interject --token <architect-token> --message "Prefer the pandas approach over pyreadstat"

unblock

Move the loop out of a paused state (blocked_on_architect or paused_by_architect) back to active. By default resumes the saved stage; override with --stage and --next-role if the situation changed.

gator loop unblock --loop <id> --message "Yes, check the v2 API docs, that's the right source"

end

Stop the loop cold from any non-terminal state. Records a reason. Different from plan_approved — there's no plan blessing, just a deliberate stop.

gator loop end --token <architect-token> --reason "Scope changed, starting over with a new sketch"
Distinction worth knowing

blocked_on_architect and paused_by_architect both land you at "waiting for architect unblock," but the origin differs — the first is a model calling escalate because it's stuck; the second is the Architect calling pause deliberately. The residue tells you which happened, so you can debrief accordingly.

When the loop ends

Four ways a loop can terminate. The residue directory persists in every case — reading it is how you learn what happened.

Terminal state What it means What to do
plan_approved Reviewer approved with --approve. Plan is signed off. Use plan.current.md to guide implementation. Optionally commit the loop directory as governance residue.
max_rounds_exceeded Revision ceiling hit without approval. Read final plan + findings. Either accept as-is, or start a new loop with --max-rounds bumped and the current plan as the new sketch.
turn_timed_out A model didn't submit within --turn-timeout. Start a new loop with a longer timeout, or check whether the model actually joined.
ended_by_architect You called gator loop end. Reason is in the session record. Do whatever comes next based on why you stopped.
No autonomous commits

The loop never commits anything to Git on its own. The residue directory is tracked-safe (session state + events are non-secret), but the .tokens.json file is gitignored. When and whether to commit the loop residue is entirely the Architect's call.

What can go wrong

Symptom What's actually happening Fix
Model submits garbage or edits loop files directly Model didn't read the protocol; skipped gator loop status. Re-orient the model. Protocol lives at procedures/gator-loop-protocol.md. Rule 2: the CLI is the only authorized writer.
"requires role 'draftor', got 'reviewer'" (or similar) You gave a model the wrong token. Check the banner. Draftor token to the draftor session, reviewer token to the reviewer session. Architect token stays with the Architect.
Model claims to have submitted but nothing shows in the host Model called something other than submit-draft/submit-review. Have the model re-run gator loop status. It'll show the actual state; the model can retry with the right command.
Timeout fires but the model was mid-response --turn-timeout is too short for how slowly the model is responding. Loop ended in turn_timed_out — start a new one with a bigger timeout. Model latency varies a lot by vendor and load.
Two loops in flight, mixed up which is which Multiple loops running concurrently, tokens got confused. gator loop list to see them all. Loop IDs are date-stamped; the banner from gator loop start shows the ID clearly.
Model escalates repeatedly Sketch is genuinely ambiguous, or the model doesn't have enough context. Unblock with a --message that resolves the ambiguity. If it keeps happening, end the loop and rewrite the sketch.
