# Charter history archive: Cross-Cutting

The cross-cutting charter is read at the start of every session, so it states only current contracts. On 2026-11-07 its dated history (issue tags, dates, checkpoint and loop names, version notes, and change-log wording such as "gains" or "is replaced by") was removed and the affected sections were restated as current contracts. No rule, field, tolerance requirement or test pin was dropped. The sections below are the previous text, verbatim, so the history stays readable outside Git.

## TRIPWIRE: Runtime and Hook Dispatch (loop watchers and session.json paragraph)

Loop watchers (CLI `start`/`extend` foreground hosts and Dashboard daemon threads) decide to stop from the **session**, not the event log: a terminal event ends a watch only while `session.json` is still terminal, because `max_rounds_exceeded` is resumable via `extend` (#39). Any new watcher or poller that treats a terminal event as final must re-check the session. Every loop revival (start or extend) holds `start.lock` and refuses when another loop is active; see [`scripts-loop.md`](scripts-loop.md). The Dashboard serves requests concurrently (`DashboardHTTPServer`, threaded-server plan). Its own state locks (`_STATE_WRITE_LOCK`, `_STATE_LOCK`) are never held while a Loop OS lock (`start.lock`, `host.lock`, `session.lock`, the liveness lock) is acquired, and `_LOOP_HOSTS_LOCK` stays a leaf. The Loop locks remain the only authority for Loop transitions; see [`scripts-dashboard.md`](scripts-dashboard.md). **`session.json` sharing violations (#61):** on Windows, Loop saves and reads of `session.json` retry a transient sharing violation briefly, and never write the file in place. When retries run out, `loop/session.py` raises `SessionBusyError` (an `OSError` with errno `EBUSY`, not a `PermissionError`): nothing was written. Every consumer must treat it as "busy; retry". The Dashboard maps it to 503 "loop is busy; retry" (`_LOOP_LOCK_BUSY_ERRNOS`). The single-active guard `host.find_active_loop()` counts that loop as active (fail closed). Readers that catch `OSError` poll again. See [`scripts-loop.md`](scripts-loop.md).

## TRIPWIRE: CLI and Git Compatibility

Machine-readable CLI output has a top-level `schema` identifier. Additive fields may remain within a version; removing, renaming, or changing meaning requires a schema bump and consumer migration. Example: `gator-loop-status-v1` gained `turn_timeout_seconds` / `turn_deadline` (status and wait) and bounded-wait fields additively; the Dashboard and agents must tolerate their absence in older output.

Loop turn windows (legacy) and Architect attention intervals (#47; same stored field) have one validation authority: `loop/session.validate_turn_timeout()` (30..3600 s, integral). The loop CLI (`unblock --timeout`, legacy loops only; attention-mode loops refuse it) and the Dashboard HTTP endpoints (loop start `attention_interval` / alias `turn_timeout`, unblock `timeout` for legacy loops only, via `_validate_http_turn_timeout()`) must both route through it; the browser mirrors the bounds only for early feedback. Do not re-implement the range at a call site. The per-extension round increment follows the same rule via `validate_round_count()` (1..20) — CLI `extend --rounds` and Dashboard `/extend` (`_validate_http_round_count()`).

**Machine-local commit policy (2026-10-28; `hook-mode-vocabulary-v2`).** The commit policy is per engineer and per clone. It lives in `$(git rev-parse --git-path gator-commit-policy.json)` (`precommit_local_policy.py`), is never tracked, and is `strict` when absent; the local levels are `strict | warn`. The tracked `.gator/config.json` `enforcement_level` is no longer read by either hook copy. This is a deliberate meaning change: a committed `warn`/`off` is ignored, with a warning. The Enterprise bundled hook falls back to `strict` when `GATOR_HOOK_MODE` is unset. The additive trailer `Gator-Commit-Policy: warn` marks a commit made under a relaxed policy; strict commits carry none, and readers must tolerate its absence on every historical commit. `POST /api/repo/<name>/config` is replaced by `POST /api/repo/<name>/commit-policy` (no external callers). `precommit_local_policy.py` exists byte-identically in `templates/gator-starter/scripts/` and `scripts/` (and `gator-enforce.py` as before), pinned by `tests/test_local_commit_policy.py`; `scripts/precommit_local_policy.py` is in `package-data`. See `scripts-precommit.md` (TRIPWIRE: The Commit Policy Is Machine-Local).

Commit readers accept both `Gator-Architect` and legacy `Gator-PI`. New commits emit `Gator-Architect`; historical trailers remain valid input.

Override audit trailers (#34, #35) are additive: `Gator-Override-Approved-By` and `Gator-Override-Block` (pre-existing), plus `Gator-Override-Reason` and `Gator-Override-Rules` (comma-separated rule names). All values are single-line and bounded by `precommit_override.sanitize_trailer_value()` so Architect input cannot inject trailers. The bounds are `TRAILER_MAX`: approver 80, reason **500** since 2.35.0 (200 before). Trailer readers (Commits view, audit) must not assume the older 200-character reason. Readers must tolerate their presence or absence. `Gator-Charter-Changed: override-skip` appears only when an Architect approval overrode a charter rule (#75 keeps that as the charter escape hatch). `Gator-Override-*` is reserved for an actual external approval: a charter override, or a dangerous pattern in Enterprise `evidence_only`. Approvals carry an additive `resolution_policy` marker in `approval.json` (machine-local state, not a trailer).

Architect acknowledgement trailers (#75) are additive: `Gator-Dangerous-Patterns` (comma-separated `RULE@path:line` keys, never the matched source text; a key keeps its path's internal whitespace byte-for-byte, so readers split on `,` only) and `Gator-Dangerous-Pattern-Acknowledged-By` (the sanitized `architect` field). A recorded skip adds `Gator-Dangerous-Patterns-Unacknowledged` (comma-separated keys): the agent proceeded without an Architect decision. These are emitted only for evidence that validated against the commit's staged change, are not override evidence, and readers must tolerate their absence on every historical commit. `status.json` gains the additive `commit_checks` object (rule names and keys only).

The `change-type`, `significance`, vendor, and source-kind vocabularies are shared contracts. Update producers, schemas, compatibility tests, and consumers together.

**Commits view as a trailer and vocabulary consumer (2026-10-19).** The Dashboard Commits view reads commit trailers through `dashboard/data.py` `get_repo_history()`, which projects every `Gator-*` trailer in order and folds legacy `Gator-PI` into `architect`. It renders them in `views/history.js`.
- **`change-type`:** `KINDS` labels every value in the producer's `VALID_CHANGE_TYPES`. An unknown value gets a neutral label. `tests/test_dashboard_ui/test_commits_view.py` fails if the producer adds a type the view does not label, so a vocabulary change must update the view too.
- **`significance`:** only `notable` gets a flag; any other value is shown as text.
- **Override trailers:** they are optional; the view shows an override note only when one is present.
- **Acknowledgement trailers (#75):** optional; the view shows a separate "✓ Architect acknowledgement" note and "✓ Acknowledged" tag, never an override note, when `Gator-Dangerous-Patterns` is present.
- **`Gator-Machine-Id`:** shown only in the view's Raw trailers.

See `scripts-dashboard.md` → `get_repo_history()` and `scripts-dashboard-ui.md` → Commits view.

## Package and License Surface (package-data paragraph)

`src/gator_command/cli.py` is the installed command router. Adding or removing a public subcommand requires coordinated parser, packaging, help, and installed-wheel coverage. `VERSION` and `pyproject.toml` version fields must agree; the release-candidate workflow validates this. `[tool.setuptools.package-data]` lists script files explicitly, so every new module under `scripts/` (for example `scripts/loop/liveness.py`) must be added there, as with `scripts/loop/gitsnap.py` (#41), `scripts/loop/codex_launcher.py` (#37 follow-up) and `scripts/charter_covers.py` / `charter_report.py` / `gator-charters.py` (charters-health-section); `tests/test_packaging.py` guards the gap. **Exception: Dashboard assets** ship through the `scripts/dashboard/**/*` glob (only `views/audit.js` is excluded), so a new `scripts/dashboard/views/*.js` or shell module such as `scripts/dashboard/workspace.js` (#80) needs no `package-data` entry. It must instead be added to both the script-tag regex and the inlined block in `dashboard/snapshot.py` `build_snapshot()`, or the offline snapshot keeps an external reference. `views/loop-markdown.js` (#45), `workspace.js` (#80) and `views/charters.js` (charters-sidebar-sync) are examples, pinned by `tests/test_snapshot.py`. **Runtime read of starter templates (Welcome HTML documents):** the Dashboard serves the shipped Gator documents `templates/gator-starter/docs/{gator-overview,what-gator-can-do,gatorize-a-repo,start-a-session,gator-docs,gator-loop,gator-loop-extras,pre-commit-checks,charter-formation-process,charter-schema-v1,code-migrations}.html` at runtime (Welcome and the repo-independent Docs view, 2026-10-13; the Loop Help and Extras tabs, 2026-10-24) (`dashboard/helpers.WELCOME_DOCS_DIR` / `WELCOME_DOC_NAMES`, package-relative). It therefore depends on the `templates/**/*` package-data glob shipping them. Moving or renaming one breaks its Welcome topic: the route degrades to a plain-text 404, and the snapshot inlines `null`. The same files reach governed repositories through the generic `docs/` overlay in both `gatorize` (`action_install_gator()`) and `gator update` (`USER_TEMPLATE_DIRS["docs"]`); no installer code names them. Pinned by `tests/test_packaging.py::test_wheel_has_templates` and `tests/test_welcome_docs.py`.
